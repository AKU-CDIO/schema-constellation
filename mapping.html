Data Mapping Guide

Keys to Data Mapping

The AKU Meditech Data Repository exposes your EMR data in a SQL database — AKULiveATdb.dbo — with more than 17,000 tables and 143,000 columns. This guide shows you the catalog views that map where each piece of data lives, how to read a table's key level, and the query patterns to pinpoint any table or column — the same way MEDITECH's SysDrTables / SysDrColumns work in a native Data Repository.

SQL Tables for Data Mapping

The catalogs that tell you what exists

Every SQL Server database exposes system catalog views that describe the database itself — they contain no hospital data, only structure. These are your mapping tables. Two matter most:

INFORMATION_SCHEMA.TABLEStable catalog
One row per table — the equivalent of MEDITECH's SysDrTables. Run it in AKULiveATdb and every row is a table you can report from.
INFORMATION_SCHEMA.COLUMNScolumn catalog
One row per column — the equivalent of MEDITECH's SysDrColumns. Name, SQL data type, max length, position and nullability for all 143,082 columns.

In a MEDITECH-native Data Repository these same concepts are pre-built as SysDrTables and SysDrColumns. Check whether they exist in this database:

-- Does the native MEDITECH mapping layer exist here?
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'SysDr%';

If it returns rows, you can run MEDITECH's SysDrTables/SysDrColumns queries verbatim. If it returns nothing (as in the schema dump this site is generated from), the queries below give you the identical capability against the SQL Server catalogs.

Table catalog

Every table you can query, with its key level

The columns to note in the table catalog: TABLE_NAME (the MEDITECH mnemonic — e.g. EmrPat_Allergies), TABLE_CATALOG (the database — always AKULiveATdb here), TABLE_SCHEMA (dbo), and the key level you derive from the key columns present.

-- (1) The complete list of tables available for reporting
SELECT DISTINCT TABLE_NAME
FROM AKULiveATdb.INFORMATION_SCHEMA.TABLES
WHERE TABLE_TYPE = 'BASE TABLE'
ORDER BY TABLE_NAME;

The first letters of a table name tell you the feeder application — the MEDITECH module that populates it:

-- Prefix = feeder application
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'Bar%';   -- Bar = Billing / AR (claims, insurance)
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'EmrPat%';  -- Emr = EMR patient chart (allergies, meds, labs)
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'Mis%';     -- Mis = master dictionaries (fin class, insurer, dx)
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'Abs%';     -- Abs = abstracting / diagnoses
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'RegAcct%'; -- Reg = registration / accounts
Key levels

What kind of rows a table holds

Every MEDITECH table belongs to a key level that says what its rows describe and which keys identify them. This is derived from the key columns present in the table. The counts below are real, computed from the AKU schema dump:

-- (2) Derive the key level for every table yourself
SELECT TABLE_NAME,
       MAX(CASE WHEN COLUMN_NAME='PatientID' THEN 1 ELSE 0 END) AS HasPatient,
       MAX(CASE WHEN COLUMN_NAME='VisitID'   THEN 1 ELSE 0 END) AS HasVisit,
       MAX(CASE WHEN COLUMN_NAME='SourceID'  THEN 1 ELSE 0 END) AS HasSource
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
GROUP BY TABLE_NAME;

Rule of thumb: tables with PatientID hold patient chart data, tables with VisitID (and no PatientID) hold visit/encounter data, and tables with neither are dictionaries or reference data you join on code columns.

Column catalog

Every column, with its type and length

Each row in INFORMATION_SCHEMA.COLUMNS is one column available to you. Columns to note: COLUMN_NAME, DATA_TYPE (varchar, int, datetime…), CHARACTER_MAXIMUM_LENGTH, ORDINAL_POSITION (the column's position from the left), and IS_NULLABLE.

-- (3) All columns of one table, in table order
SELECT COLUMN_NAME, ORDINAL_POSITION, DATA_TYPE,
       CHARACTER_MAXIMUM_LENGTH AS MaxLen, IS_NULLABLE
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'EmrPat_Allergies'
ORDER BY ORDINAL_POSITION;
The mapping query

Find where any piece of data lives — or trace it back

This is the basic format to work with. Change the WHERE clause and it answers almost every mapping question. Starting with a known column name, find every table that carries it:

-- Given a column name → which tables have it?
SELECT DISTINCT TABLE_NAME
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE COLUMN_NAME = 'AllergenID';

Real result for AllergenID: it lives in EmrPat_Allergies, EmrPat_Allergies_AllrgComment and EmrPat_Allergies_AllrgDeleteReason — the allergy table and its per-row text/delete sub-tables.

Add the table catalog to make it self-explanatory — this is the flagship query, the one to remember:

-- Column name → table, position, type (the "make it this query" pattern)
SELECT c.TABLE_NAME, c.COLUMN_NAME, c.ORDINAL_POSITION,
       c.DATA_TYPE, c.CHARACTER_MAXIMUM_LENGTH AS MaxLen
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS c
WHERE c.COLUMN_NAME = 'Address1'
ORDER BY c.TABLE_NAME;

Real result: Address1 appears in 34 tables — e.g. BarAcctRefund_SendToAddress, BarAcctRep_Address, BarClaimFormat_Address. The same column name in different tables means the same MEDITECH element flows to several places.

Or reverse the process — given a table, list its columns; given a column, see the type:

-- Reverse: table → its columns (the Address1 example from the newsletter)
SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH AS MaxLen
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'AdmVisits'
ORDER BY ORDINAL_POSITION;

And because MEDITECH stores dictionary codes with a suffix, a column ending in a code (e.g. Insurance_MisInsID, FinClass_MisFinClassID) is a foreign key into the matching Mis* dictionary. You can find every table that reads a given dictionary:

-- Which tables read the insurance dictionary (MisIns_Main)?
SELECT DISTINCT TABLE_NAME
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE COLUMN_NAME = 'Insurance_MisInsID';

Real result: 77 tables join to the insurance dictionary — claims, authorizations, benefit periods, reimbursement rates, and the curated insurance topics in this explorer.

NPR element trace

Where data originates in MEDITECH (Shift+F9)

In a MEDITECH application you can press Shift+F9 in any field to see its NPR DPM, Segment and Element (e.g. ADM.PAT.street). This guide's catalogs give you the SQL side of that mapping. To complete the backward trace from a SQL column to the MEDITECH element that populates it, you need the native mapping layer:

  • If SysDrColumns exists in the database (check above), run the newsletter's query joining SysDrTables ↔ SysDrColumns on TableID and filter on NprElement.
  • Otherwise use Shift+F9 in the EMR for the exact NPR element, then find the SQL home with the mapping query above.
  • Fields marked “Not captured by DR” come from temporary screen structures — find the underlying data-structure table with the same pattern.
