Chronological workflow

MEDITECH's method, translated to the AKU evidence

Follow these steps in order. Each step states what MEDITECH's native mapping layer would provide, what INFORMATION_SCHEMA can reproduce here, and where a procedure or human validation is still required.

01
Set the evidence boundary

Confirm the database: this AKU extract contains no SysDrTables or SysDrColumns. Do not claim official NPR lineage or MEDITECH Keylevel values.

 02
Inventory reportable tables

Use INFORMATION_SCHEMA.TABLES in place of the SysDrTables list. TABLE_NAME and TABLE_SCHEMA are available; TableID, Application and Keylevel are not.

 03
Classify candidate grain

MEDITECH defines PS, PM, PF, PV, V, VF, NP, T and D. AKU can only infer P?, PV?, V? and NP? from PatientID and VisitID until native metadata is supplied.

 04
Inventory columns

Use INFORMATION_SCHEMA.COLUMNS for name, type, length, position and nullability. SortKey, NprDpm, NprSegment and NprElement remain unavailable.

 05
Locate data in either direction

Search a known SQL column across tables or list a known table's columns. Matching names create candidates; they do not prove a shared NPR element.

 06
Resolve MEDITECH lineage

Use Shift+F9, Table Inquiry or Field Inquiry for DPM, segment and element. Request an authorized SysDr export when production lineage must be proven.

 07
Link and test tables

Prefer joins already used by checked-in procedures. For inferred PI + VI or SI + VI links, test uniqueness, nulls, orphans and row amplification.

 08
Operationalize the topic

Review the Explorer graph, run the topic assembly query, inspect the stored procedure, then execute its validation query before publication.

Step 2 - Table catalog

Every table you can query, with a candidate grain

The available catalog fields are TABLE_NAME (for example EmrPat_Allergies), TABLE_CATALOG (AKULiveATdb here), TABLE_SCHEMA (dbo) and TABLE_TYPE. Candidate row grain is inferred separately from marker-column presence and must not be presented as MEDITECH's official Keylevel.

-- (1) The complete list of tables available for reporting
SELECT DISTINCT TABLE_NAME
FROM AKULiveATdb.INFORMATION_SCHEMA.TABLES
WHERE TABLE_TYPE = 'BASE TABLE'
ORDER BY TABLE_NAME;

Table-name prefixes can help narrow a search and often suggest a MEDITECH module, but without SysDrTables.Application they are naming heuristics, not authoritative feeder-application metadata:

-- Prefix = feeder application
SELECT TABLE_NAME FROM INFORMATION_SCHEMA.TABLES
 WHERE TABLE_NAME LIKE 'Bar%';   -- Bar = Billing / AR (claims, insurance)

Step 3 - Candidate grain

What marker columns suggest - and what they do not prove

Because official Keylevel and SortKey metadata are unavailable, the site assigns a candidate grain family only from the presence of PatientID, VisitID and SourceID. The question marks are deliberate: these labels do not distinguish primary keys from foreign keys or singular from repeating rows. The counts reconcile to all 17,094 base tables:

-- (2) Reproduce the detected grain family for every base table
WITH ColumnFlags AS (
  SELECT TABLE_NAME,
         MAX(CASE WHEN COLUMN_NAME='PatientID' THEN 1 ELSE 0 END) AS HasPatient,
         MAX(CASE WHEN COLUMN_NAME='VisitID'   THEN 1 ELSE 0 END) AS HasVisit,
         MAX(CASE WHEN COLUMN_NAME='SourceID'  THEN 1 ELSE 0 END) AS HasSource
  FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
  GROUP BY TABLE_NAME
)
SELECT TABLE_NAME,
       CASE
         WHEN TABLE_NAME LIKE 'DR[_]%' AND HasSource=0 AND HasPatient=0 AND HasVisit=0 THEN 'SYS?'
         WHEN HasPatient=1 AND HasVisit=1 THEN 'PV?'
         WHEN HasPatient=1 THEN 'P?'
         WHEN HasVisit=1 THEN 'V?'
         ELSE 'NP?'
       END AS CandidateGrain
FROM ColumnFlags
ORDER BY TABLE_NAME;

Interpretation rule: PatientID and VisitID identify candidate grain only. Confirm uniqueness, null rates, orphan rates and join amplification before declaring a production relationship. A table with neither marker is simply unclassified from this evidence; it must not automatically be called a dictionary or non-patient table.

Step 4 - Column catalog

Every column, with its type and length

Each row in INFORMATION_SCHEMA.COLUMNS is one column available to you. Columns to note: COLUMN_NAME, DATA_TYPE (varchar, int, datetime…), CHARACTER_MAXIMUM_LENGTH, ORDINAL_POSITION (the column's position from the left), and IS_NULLABLE.

-- (3) All columns of one table, in table order
SELECT COLUMN_NAME, ORDINAL_POSITION, DATA_TYPE,
       CHARACTER_MAXIMUM_LENGTH AS MaxLen, IS_NULLABLE
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'EmrPat_Allergies'
ORDER BY ORDINAL_POSITION;
Step 5 - The mapping query

Find where any piece of data lives — or trace it back

This is the basic format to work with. Change the WHERE clause and it answers almost every mapping question. Starting with a known column name, find every table that carries it:

-- Given a column name → which tables have it?
SELECT DISTINCT TABLE_NAME
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE COLUMN_NAME = 'AllergenID';

Real result for AllergenID: it lives in EmrPat_Allergies, EmrPat_Allergies_AllrgComment and EmrPat_Allergies_AllrgDeleteReason — the allergy table and its per-row text/delete sub-tables.

Add the table catalog to make it self-explanatory — this is the flagship query, the one to remember:

-- Column name → table, position, type (the "make it this query" pattern)
SELECT c.TABLE_NAME, c.COLUMN_NAME, c.ORDINAL_POSITION,
       c.DATA_TYPE, c.CHARACTER_MAXIMUM_LENGTH AS MaxLen
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS c
WHERE c.COLUMN_NAME = 'Address1'
ORDER BY c.TABLE_NAME;

Observed result: Address1 appears in 34 tables - e.g. BarAcctRefund_SendToAddress, BarAcctRep_Address, BarClaimFormat_Address. Repeated names identify candidates to investigate; without NprElement metadata they do not prove that the same MEDITECH element populates every column.

Or reverse the process — given a table, list its columns; given a column, see the type:

-- Reverse: table → its columns (the Address1 example from the newsletter)
SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH AS MaxLen
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'AdmVisits'
ORDER BY ORDINAL_POSITION;

A dictionary-style suffix (for example Insurance_MisInsID or FinClass_MisFinClassID) is useful evidence for a candidate link to a matching Mis* table. Confirm it with stored-procedure usage and relationship-quality queries before treating it as a foreign key:

-- Which tables read the insurance dictionary (MisIns_Main)?
SELECT DISTINCT TABLE_NAME
FROM AKULiveATdb.INFORMATION_SCHEMA.COLUMNS
WHERE COLUMN_NAME = 'Insurance_MisInsID';

Observed result: 77 tables contain the candidate insurance key. That is discovery evidence, not proof that all 77 joins have the same cardinality or business meaning.

Step 6 - NPR element trace

The remaining evidence gap

MEDITECH's guide uses SysDrColumns.NprDpm, NprSegment and NprElement to trace a SQL column back to its source. Those fields are not present in the supplied AKU catalog, so this site cannot validate backward NPR lineage on its own.

  • Use Shift+F9 on the MEDITECH field to capture its NPR DPM, segment and element.
  • Use MEDITECH Table Inquiry or Field Inquiry when available to resolve the corresponding SQL table and column.
  • For production-grade lineage, request a read-only export of TableID, Application and Keylevel plus TableID, Name, SortKey, NprDpm, NprSegment, NprElement and ColumnPosition from an authorized TEST or LIVE Data Repository that has the native mapping layer.
  • Until that evidence is imported, label mappings as schema-confirmed, procedure-confirmed or inferred; never label them NPR-confirmed.
Step 7 - Production relationship gate

Validate a candidate join before using it in an SP

This example checks the visit-grained infusion source against the encounter spine. A production-ready relationship should return zero orphan rows, zero rows attached to a duplicated parent key, and a maximum of one parent match.

-- Validate PcsMarAct_MarLastDocumented -> AdmVisits
WITH ParentKey AS (
  SELECT SourceID, VisitID, COUNT_BIG(*) AS ParentRows
  FROM AKULivendb.dbo.AdmVisits
  WHERE VisitID IS NOT NULL
  GROUP BY SourceID, VisitID
),
ChildKey AS (
  SELECT SourceID, VisitID, COUNT_BIG(*) AS ChildRows
  FROM AKULiveATdb.dbo.PcsMarAct_MarLastDocumented
  WHERE VisitID IS NOT NULL
  GROUP BY SourceID, VisitID
)
SELECT SUM(c.ChildRows) AS ChildRows,
       SUM(CASE WHEN p.VisitID IS NULL THEN c.ChildRows ELSE 0 END) AS OrphanRows,
       SUM(CASE WHEN p.ParentRows > 1 THEN c.ChildRows ELSE 0 END) AS AmbiguousParentRows,
       MAX(COALESCE(p.ParentRows,0)) AS MaxParentMatches
FROM ChildKey c
LEFT JOIN ParentKey p
  ON p.SourceID=c.SourceID AND p.VisitID=c.VisitID;

Repeat this gate for every inferred relationship. For patient grain use SourceID + PatientID; for table-family detail use the full shared key, such as SourceID + CwsApptID.
